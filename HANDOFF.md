## 1. Что решалось

Задача: ассистент внутри редактора ставит в макет блок (таблицу, карточку) из
компонентов дизайн-системы. Блок должен встать в **слот**, сохраниться в файл
и пережить перезагрузку. Мастера дизайн-системы при этом трогать нельзя.

Наблюдаемое поведение до работы: блок показывался на канвасе и **исчезал после
сохранения**; ассистент либо бросал задачу с объяснением, либо падал с ошибкой
про `figma is not defined`, либо попадал не в тот узел.

---

## 2. Что выяснено о формате и механике

Это главное знание — без него следующие правки будут вслепую.

### 2.1. Слот — это свойство компонента, а не пометка

В Figma место под содержимое — **свойство компонента типа `SLOT`**
(в файле `ComponentPropType.SLOT = 7`), на которое фрейм ссылается полем
`ComponentPropNodeField.SLOT_CONTENT_ID`.

Проверка: в `ds-main` найдено **494 узла со ссылкой на слот**, из них
**461 с содержимым**. Формат это умеет — механизм рабочий.

Наша прежняя пометка в `pluginData` формату неизвестна: содержимое, положенное
в такой фрейм, показывается на канвасе и **пропадает при сохранении**.

### 2.2. Наполнять надо слот мастера

Содержимое, положенное прямо в копию (узел внутри инстанса), **в файл не
пишется**. Работает только путь: правка уходит в **мастер** слота, копии
получают содержимое при открытии.

Проверка (сквозной прогон с записью и чтением): блок, положенный в слот
мастера, найден после сохранения и в слоте мастера, и в обоих слотах копий.

### 2.3. Слот копии знает своего мастера

Фрейм-слот внутри инстанса несёт `componentId`, указывающий на тот же фрейм в
мастере. По этой связи и надо находить, куда наполнять. Само свойство живёт
**у мастера**.

### 2.4. Номера узлов не были постоянными

Это объясняет большую часть «непонятных» отказов: инструмент звал узел по
номеру, добытому шагом раньше, и попадал в чужой узел.

Причина — три места выдачи номеров:

| Где | Что было |
|---|---|
| узлы из файла | номер по порядку обхода, а не из файла |
| страницы | так же |
| копии внутри инстанса | новый номер при каждом разборе (источник обнулялся) |

Проверка до правки: два разбора одного файла давали **разные** номера.
Проверка после: номера совпадают (`1:8000000788, 1:8000000796, 1:96`).

Правка — `fix(graph): номера узлов и копий не меняются между открытиями`
(PR #162). Номер берётся из файла; для копий выводится из образца и места.
**Важная тонкость:** номер должен оставаться в пределах точности чисел.
Вложенные копии наследуют производный номер родителя, и простое умножение
выводит результат за `Number.MAX_SAFE_INTEGER` — тогда номер теряет разряды.
В `packages/scene-graph/src/instances.ts` стоит сборка номера из двух частей
со смещением `INSTANCE_CHILD_ID_OFFSET = 4_000_000_000`.

### 2.5. Пометка базового варианта может устареть

`get_default_variant` возвращал номер варианта из `pluginData`. Пометка хранит
**номер узла**, номера меняются при пересборке — записанный прежде номер стал
указывать на **иконку внутри кнопки**. Инструмент уверенно возвращал её как
базовый вариант карточки, и вставка падала на «component not found».

Правка — PR #163: пометка принимается, только если ведёт к варианту того же
сета.

### 2.6. Текст отказа провайдера залипал

Отказ провайдера клался в переменную и оставался там до конца прогона.
Обработчик ошибок брал его вместо настоящей ошибки — **любая** следующая
неудача показывала чужой текст. Отсюда «figma is not defined» на `1+1`.

Правка — PR #158: память снимается перед каждым шагом.

### 2.7. Дети инстанса в файл не пишутся

`packages/fig/src/node-change/export-node.ts`:

```js
const children =
  node.type === 'INSTANCE'
    ? []                    // дети инстанса не пишутся
    : context.graph.getChildren(node.id)...
```

Это не баг, а устройство формата. Копия хранит только ссылку на мастер;
исключение — узлы-слоты, они пишутся как обычные записи.

## 4. Что осталось — следующая задача

### 4.1. Ближайшая незакрытая: цвет не сохраняется

Запрос: «Добавь пустую карточку красного цвета». Ассистент **карточку сделал,
цвет поставил**, но **цвет после перезагрузки не пришёл**, и «сломался мастер».

Разбор прогона (чат `4aaaf5f8-1d46-4755-8483-061ce778e3ee`), **7 шагов**:

```
set_fill → { "id": "0:8000001593", "color": "#FED3D3" }
render   → не вызывался
fill_slot → не вызывался
```

Что в файле после прогона:

```
1:101          "Card empty red"  заливка БЕЛАЯ  componentId=8491:18234  ← копия
1:8000001577   "Card empty red"  заливка БЕЛАЯ  componentId=1:101
1:8000001593   "Card empty red"  заливка БЕЛАЯ  componentId=1:101       ← её красил
мастер Card 8491:18234           БЕЛАЯ                                   ← не тронут
```

**Корень:** `set_fill` покрасил **номера узла, которого в сохранённом файле
нет** (`0:8000001593` — вложенная копия). Копия своих правок не хранит.

Второе: промежуточного компонента ассистент **не создал**. `1:101` — тоже
**копия** (`type: INSTANCE`, `componentId: 8491:18234`), а не компонент.
Поэтому «своего» носителя цвета нет.

### 4.2. Что предлагалось и было отклонено

Предлагалось увести `set_fill` в мастер по `componentId`. **Отклонено
пользователем:** мастера дизайн-системы трогать нельзя. Правка откачена,
дерево чистое.

### 4.3. Согласованное направление

Собирать **свой компонент** как носитель:

```
1. Создать СВОЙ компонент (например «Card red»), 425×175
2. Перенести в него нутро Card (слот, размеры) — не копированием копии
3. Покрасить СВОЙ компонент
4. fill_slot этим компонентом → в слот мастера
```

Мастера ДС при этом не тронуты: правится свой компонент, а не `Card`.

**Открытый вопрос, который надо решить с пользователем:** слот мастера
`Layout` — общий для всех экранов, а на канвасе **два** `Layout` (`1:98`,
`1:99`). Куда ставить:

| Вариант | Что |
|---|---|
| **A** | отвязать инстанс `Layout` — правки только этого экрана |
| **B** | свой компонент-обёртка вместо `Layout` целиком |
| **C** | согласиться, что оба экрана получают красную карточку |

Рекомендация ассистента — **A**: правится свой экран, мастер `Layout` цел.

| Чаты | `GET https://html.norka.cc/store/api/chats/ds-main` |

**Тяжёлые данные (`.fig`, распакованные дизайн-системы) в git не лежат** —
только на сервере. `data/` и `vite/.build-number` в `.gitignore`.

### 5.2. Сборка и выкладка

```bash
cd /opt/open-pencil-clean
bun run build:packages                    # обязательно при правках core/i18n/fig/scene-graph
bunx vite build
cp -r dist/. /var/www/openpencil/
chown -R www-data:www-data /var/www/openpencil
find /var/www/openpencil -type d -exec chmod 755 {} +
find /var/www/openpencil -type f -exec chmod 644 {} +
curl -s https://html.norka.cc/files | grep -o "<title>[^<]*"   # проверить номер сборки
```

Номер сборки берётся из `vite/.build-number` и подставляется заголовком окна.

### 5.3. Как проверять правки графа без браузера

Основной способ, которым проверялась вся эта работа — прогон в `bun` с
чтением живого файла с сервера:

```bash
cd /opt/open-pencil-clean
export PATH="/usr/local/bin:$PATH"
bun -e "
const r = await fetch('https://html.norka.cc/store/api/documents/ds-main')
const b = new Uint8Array(await r.arrayBuffer())
import * as figPkg from '/opt/open-pencil-clean/packages/fig/dist/index.js'
import * as corePkg from '/opt/open-pencil-clean/packages/core/dist/index.js'
const raw = figPkg.parseFigBuffer(b.buffer)
const g = corePkg.importNodeChanges(raw.nodeChanges, raw.blobs, new Map(), { populate: 'all' })
// здесь проверяем узлы
"
```

Для проверки именно **записи** нужен полный цикл: правка → `releaseOriginalFigArchive(g)`
→ `exportFigFile(...)` → снова `parseFigBuffer` → искать результат в прочитанном.
Без снятия архива экспорт вернёт файл как есть, игнорируя правки.

### 5.4. Грабли, на которые я наступал

- **`patch`/`write_file` на `/etc/...` отказывают** → писать через
  `terminal` + `python3` heredoc.
- **`rm` и `rsync --delete` через `terminal` виснут** → пользоваться `cp -r`.
- **Модель для ассистента:** провайдер OpenAI-compatible, Base URL
  `https://api.deepseek.com/v1`, ID модели **`deepseek-flash`** (не `deepseek-v4-flash`).
  Reasoning-модель: нужен запас токенов, иначе ответ приходит пустым.
- **Проверять надо на факте, а не по косвенным признакам.** За эту работу
  я трижды объявлял причину по имени вложенного узла или по совпадению строки,
  и трижды она была не та. Рабочий способ — воспроизвести вызов и посмотреть,
  что реально в графе и что реально в сохранённом файле.
- **Скрипты анализа дизайн-системы идут долго** (десятки тысяч узлов).

## 6. Где искать подтверждения

| Утверждение | Как проверить |
|---|---|
| Слот — свойство типа `SLOT` | в файле `ds-main` найти узлы со ссылкой `SLOT` (их 494) |
| Слоты с содержимым сохраняются | прочитать `ds-main`, посмотреть детей у слотов (461 с содержимым) |
| Номера постоянны | дважды разобрать один файл, сравнить номера |
| Дети инстанса не пишутся | `packages/fig/src/node-change/export-node.ts`, ветка `node.type === 'INSTANCE'` |
| Отказ провайдера залипал | история чатов на сервере: `/store/api/chats/ds-main` |
| Цвет не сохранился | в файле три узла `Card empty red`, все с белой заливкой |

История чатов с ассистентом лежит на сервере и читается без авторизации:
`GET https://html.norka.cc/store/api/chats/ds-main` — список, затем
`GET .../chats/ds-main/<id>` — полный прогон с шагами и ошибками. Это самый
полезный источник при разборе: видно каждый вызов инструмента и его ответ.

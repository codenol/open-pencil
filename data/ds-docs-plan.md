# Документация компонентов ДС (проектная идея)

Статус: проектирование, реализация — потом.
Дата: 19.09.2026

## Идея

Каждый компонент дизайн-системы несёт не только пиксели, но и текст для людей и для LLM:

| Слой | Что внутри |
|---|---|
| Описание | что это за компонент, для чего существует |
| Гайдлайны | как можно: когда использовать, как комбинировать |
| Гардрейлы | как нельзя: чего избегать, типовые ошибки |

Тот же материал в машиночитаемом виде → LLM в чате (AI-таб) может проверять: «не нарушаю ли я ДС».

## Пример карточки (button, черновик формата)

```yaml
component: button
level: организм
variants: State × Type × Size × Sentiment × Icon position
tokens: button.* (filled/outline/ghost/text × accent/danger/...)
uses: [icon, wine]
```
**Описание.** Кнопка запускает действие. Основной способ действия пользователя.

**Гайдлайны.**
- одна главная (filled accent) кнопка на экран/блок
- подпись — глаголом: «Сохранить», «Отправить»

**Гардрейлы.**
- не использовать для навигации (для этого — ссылка)
- не делать две конкурирующие primary-кнопки рядом
- не переносить подпись на две строки

## UI

Открыл компонент → в свойствах табы рядом с «Дизайном»: [Описание] [Правила]. Правится прямо в ДС, сохраняется вместе с компонентом, публикуется вместе с библиотекой.

## Сценарии

1. Дизайнер правит текст у компонента — как правит заливку.
2. Аналитик/новичок читает «как можно/нельзя», не открывая конвенции отдельно.
3. ИИ в чате: «проверь, не нарушаю ли я ДС» → читает карточки + макет → отвечает.
4. Генерация по рецептам → опирается на гайдлайны (что с чем сочетается).

## Что понадобится для реализации

- модель: поля у компонента (описание, гайдлайны, гардрейлы) + сериализация в файл
- публикация: тексты уезжают в библиотеку вместе с компонентами
- реестр: поля в ds-structure.json для LLM-контекста
- чтение текстов из .fig — сейчас не работает (characters пустые), это отдельная задача импорта
